# ACL membership TOCTOU — экспериментальное исправление для 1.2.8

Статус: **только тестовая ветка; не включено в main/production**. Перенос исправлений из PR #67 поверх последней 1.2.8 и расширение на пять операций.

Затронуты `update_user_group`, `delete_user_group`, `add_user_to_group`, `update_group_member`, `remove_user_from_group`.

Для каждой операции используется транзакция одного соединения MODX с блокировкой группы и индексированного диапазона строк членства `SELECT ... FOR UPDATE`, **до CAS-проверки и вызова штатного ACL-процессора**. Проверяется InnoDB для обеих таблиц, `REPEATABLE READ` и ведущий индекс `user_group`; при недоступности предпосылок — отказ `CAS_REQUIRED` без перехода к небезопасному пути.

Если индекс отсутствует, пять затронутых ACL-операций безопасно отказывают
с `CAS_REQUIRED` **до штатного процессора и изменения CAS**.

## Миграция существующих установок (CLI, без автоматического DDL)

Подготовлен инструмент `_build/migrate-acl-index.php`, который не вызывается
из транспортного пакета, API или при обновлении. Он рассчитан на явное
выполнение администратором **после резервной копии БД и остановки всех
записей MCP/Manager** на этом сайте.

Сначала выполнить только чтение метаданных:

```sh
MODX_CONFIG_CORE=/path/to/site/config.core.php php _build/migrate-acl-index.php --check
```

Результат `ACL_INDEX_MIGRATION_ALREADY_PRESENT` означает, что ведущий
индекс `user_group` уже имеется; добавлять ничего не нужно.
`ACL_INDEX_MIGRATION_REQUIRED` означает, что индекс отсутствует.

При подтверждённой копии БД и приостановленных writers запускать:

```sh
MODX_CONFIG_CORE=/path/to/site/config.core.php php _build/migrate-acl-index.php --apply --ack-backup --ack-writes-paused
MODX_CONFIG_CORE=/path/to/site/config.core.php php _build/migrate-acl-index.php --check
```

Никаких паролей, токенов, ACL-строк или разрешений инструмент не изменяет.
Он проверяет InnoDB у таблицы пользователей/групп, валидирует имена таблиц
и схему, проверяет наличие уже подходящего ведущего индекса (в том числе
с другим именем), запрещает коллизию имени нового индекса и использует
`ALTER TABLE ... ADD INDEX (user_group), ALGORITHM=INPLACE, LOCK=NONE`.
Ожидание блокировок ограничено пятью секундами; нет перехода на
`COPY`/`LOCK=SHARED` при неподдерживаемой версии СУБД. При сбое DDL
оператор **не должен** автоматически повторять операцию без новой
проверки `--check` и readback. Установка индекса может потребовать
временного свободного места и ожидания метаданных даже с `LOCK=NONE`.

CI проверяет **на старой чистой схеме**, что пять ACL-команд отказали до
индекса, затем выполняет настоящую миграцию на одноразовой БД MODX 2/3,
повторяет `--apply` (идемпотентность), проверяет `--check` и обычные
CAS/ACL-конкурентные сценарии. Специальный `--ci-disposable` требует
сразу трёх независимых признаков GitHub runner и БД `modx_build`,
безопаснее обычного `--apply` с ручным подтверждением.

**Граница:** скрипт намеренно не запускается на production автоматически.
Для конкретного сайта перед выполнением требуется сверить его MySQL/MariaDB,
способ резервного копирования и возможность остановить все записи; он не
решает автоматически проблему параллельных посторонних приложений.


Обязательные регрессии: внешняя запись Manager до начала или во время транзакции, пустой диапазон (phantom insert), add/update/remove, удаление группы, отказ записи ревизии, неверный индекс и изоляция, deadlock/timeout, MODX 2/3 и независимый MCP-readback. Текущая CI-матрица испытывает пять конкурентных вставок и отсутствие индекса; сценарии конкурентного изменения роли и удаления членства, а также реальные внешние эффекты плагинов остаются release-gates до независимых испытаний.

DB rollback не отменяет внешние плагины, файлы и сообщения. Не обещать абсолютную атомарность ACL-событий. При неясном исходе остановиться без автоматического повтора и сообщить `MUTATION_OUTCOME_UNCERTAIN` после запуска процессора; безопасные ранние отказы должны быть отличимы от частичного выполнения.

Дополнительно испытаны независимые транзакции Manager для изменения роли участника и удаления членства. На временной БД проверяется отказ всех пяти операций при уровне изоляции READ COMMITTED без выполнения native processor или CAS-сдвига.

Обход через универсальный `run_processor`: даже при явном privileged allowlist запрещены `security/group/*` и `security/user/group/*`; для универсальных `security/user/create|update` запрещены скрытые поля групп/ролей. Обычные согласованные процессоры не блокируются. Запрет действует на уровне ProcessorAccessPolicy до запуска native processor.
