# MODX MCP 1.2.8 — проверка журналов на секреты

Статус: проверка в **тестовой** 1.2.8. Реальные сайты и production-логи не читаются и не изменяются.

## Выявленная проблема

Ранее `AuditSupport::log()` применял маскирование по именам ключей и типичным строкам `password=`/`token=`. Но значения свободных полей `content`, `name`, `path`, `pagetitle`, `processor`, `tv_keys` и произвольные пояснения могли попасть в `core/components/modxmcp/logs/audit.log` и журнал MODX, если содержали секрет без распознаваемого маркера.

Это **потенциальная подтверждённая по коду утечка**: воспроизводится синтетическим маркером, а не обнаружена на production.

## Исправление

- Новый аудит записывает только безопасные служебные данные: имя действия из допустимого формата, тип, числовые идентификаторы, служебные статусы из закрытого набора. Произвольные строки и списки заменяются `[OMITTED]`; ключи паролей/токенов — `[REDACTED]`.
- Существующий инструмент `modx_read_audit_log` перед отправкой старых записей применяет **такое же ограничение полей**, чтобы не выдавать историю, в которой могли сохраняться исходные данные.
- Новые файлы аудита создаются приватными (`audit.log` — 0600, каталог — 0700); существующий журнал перед записью ограничивается правами. Прямой симлинк на каталог/файл отклоняется. Это **не** доказательство полной защиты от межпроцессной файловой гонки.
- Node MCP больше не печатает в stderr необработанные stdout/stderr/исключения внешнего audit-hook или полные пути резервных копий.
- Статусы выполнения и цифровые идентификаторы сохраняются; поля `payload.content`, `payload.path`, свободные заголовки и имена TV более не являются частью доступной диагностики.

## Испытания

Тесты с искусственными значениями, в том числе **без** слов password/token, проверяют три направления: запись `audit.log`, выдачу старых записей через MCP, а также stderr Node при произвольном ответе внешней команды. На одноразовых MODX 2/3 дополнительно проверяются настоящие права каталога/файла и отсутствие маркера в новых записях.

## Ограничения и действия администратора

1. **Старые файлы аудита могут физически содержать секреты**. Исправление чтения MCP не очищает их с диска. Для существующих установок требуется отдельно согласованная проверка с владельцем, резервное копирование, изоляция, безопасная ротация или удаление по правилам хранения. Автоматически менять production-логи нельзя.
2. `modx_read_error_log` читает общий журнал MODX, который могут заполнять сторонние плагины. Редактор скрывает распространённые форматы секретов, однако произвольную строку без меток невозможно надёжно отличить от обычного текста. Не считать маскирование математической гарантией, хранить error.log в закрытом контуре и ограничивать право `ops`.
3. Опциональный внешний audit-hook получает контекст, сформированный MCP, и запускается как доверенный локальный процесс. Его **собственные** файлы и доступные ему переменные окружения не проверяются этим PR. Вывод hook в stderr MCP подавлен, но администратор обязан отдельно оценивать доверие к установленному hook.
4. Системные логи PHP-FPM, nginx, reverse proxy и логи сторонних MODX-дополнений находятся вне контракта встроенного `audit.log`. Для них нужен собственный контроль хранения и доступа.

Цель данного исправления — исключить произвольные значения из **журнала, который создаёт сам MODX MCP**, и из его MCP-выдачи; не заявлять, что секретов не может быть ни в одном журнале инфраструктуры.
