# Обязательный CAS в тестовой ветке MODX MCP 1.2.8

**Статус:** тестовый код в [Draft PR №49](https://github.com/rumata-estor/modx3-mcp/pull/49). Изменения не установлены ни на один сайт и не перенесены в `main`.

## Контракт изменяющих операций

Каждая из 116 зарегистрированных мутирующих команд, независимо от источника вызова (MCP-клиент, HTTP API, процессор, неактивная возможность), должна передать `_runtime_preconditions`:

```json
{
  "observed_site_revision": 42,
  "strict_site_revision": true,
  "read_set": []
}
```

- `observed_site_revision`: целое неотрицательное число, полученное через `get_site_state` в момент чтения данных, **не синтезированное перед отправкой изменения**.
- `strict_site_revision`: только булево `true`; `false`, `1` и отсутствие ключа запрещены.
- `read_set`: массив прочитанных зависимостей и целей с SHA-256 fingerprint; сейчас допускается пустой массив только для контроля общей ревизии, **не обеспечивающего защиту от изменений через админку MODX**.
- Для `update_resource_tvs` дополнительно обязательны исходные сырые `expected_tvs` **для каждого** изменяемого TV.

Если предусловия отсутствуют или некорректны, возвращается `CAS_REQUIRED` до выполнения мутирующей операции. При неверной ревизии возвращается `STALE_STATE`. Нельзя автоматически менять устаревшую ревизию на текущую ради повторного выполнения: агент обязан перечитать данные и заново согласовать намерение.

Диспетчер MODX 2 и 3 выполняет проверку под общей блокировкой перед записью. При недоступном модульном Runtime или отсутствующем зарегистрированном инструменте возвращается `CAS_RUNTIME_REQUIRED`: возвращение к старому обработчику не разрешено. Устаревшие клиенты, которые не умеют передавать CAS, **теряют право записи**, а не получают обходной маршрут.

`get_site_state` и `get_capabilities` теперь возвращают `cas_required=true`. Все инструменты записи в MCP-клиенте объявляют `_runtime_preconditions` обязательным полем JSON Schema. Клиент дополнительно проверяет основные поля до выполнения резервного копирования и HTTP-запроса.

## Ограничение ревизии сайта и следующий этап

**Обязательность `observed_site_revision` — ещё не полная защита от параллельных правок вне MCP.** Редактор через MODX Manager не обязан увеличивать `modxmcp.site_revision`. Если запрос использует `read_set: []`, такой конфликт может остаться незамеченным.

Следующий шаг — строгое сопоставление целевого объекта с ранее прочитанным fingerprint (или raw TV CAS) для всех поддерживаемых целевых мутаций. Для действий без способа прочитать подтверждаемое состояние нужна отдельная политика отказа, а не фиктивный `read_set`.

**CAS проверяет состояние, но не выдаёт право на изменение.** Независимая авторизация подписанными разрешениями — следующий самостоятельный этап. Никаких исключений по клиенту, Site Agent, Telegram или HTTP не добавлять без документированной модели безопасности.

## Проверки и совместимость

- Unit: `_build/test.cas-required-contract.php` — 16 положительных и отрицательных проверок формата.
- Client schema: `_build/test.cas-client-contract.py` — паритет 116 команд.
- Disposable MODX2/3: `_build/test.ci-cas-required.php` — 116 запросов без CAS обязаны отказать, шесть неверных форматов отклоняются, устаревшая ревизия отклоняется, отключённый модульный Runtime не открывает старый маршрут.
- Существующие транзакционные и файловые интеграционные тесты перенесены на строгий CAS. Только **тестовая вспомогательная функция** делает `get_site_state` перед тестовой мутацией; она не входит в релизный клиент или сервер.

Проверка отказов, ревизии и редактирования выполняется на одноразовых MODX 2 / MODX 3 в CI. Стабильная 1.2.7 не меняется. Финальный релиз 1.2.8 не допускается до проверки внешних клиентов и определения политики fingerprints для целевых объектов.
