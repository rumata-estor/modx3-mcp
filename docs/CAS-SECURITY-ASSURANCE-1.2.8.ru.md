Два реальных PHP-процесса с одинаковым снимком обновляют файл: один выполняется, второй получает `STALE_STATE`.
4. **Критические операции:** запрет до запуска `install_package`, `uninstall_package`, `run_processor`, `regenerate_token`, `empty_recycle_bin`. Реальная установка или удаление пакета в CI не производится.

6. **Пути медиафайлов:** 21 синтаксический тест и шесть сценариев через MCP отвергают traversal (`../`), недопустимые имена и управляющие символы. Нормальные операции продолжают работать.

[Прогон всех 104 gate-проверок и конкурентных файловых операций](https://github.com/rumata-estor/modx3-mcp/actions/runs/44930600618); [проверка path traversal](https://github.com/rumata-estor/modx3-mcp/actions/runs/44931045256).

Это делается только в одноразовых средах GitHub Actions; тесты отказываются работать вне них.

## Семантика ошибок — не путать

- **DB атомарность:** транзакция успешно фиксирует и данные, и `site_revision`, либо откатывает оба изменения. Это относится только к покрытому набору DB-мутаторов, при поддержке транзакций таблицами и одним DB-подключением.
- **External revision reservation:** запись новой ревизии происходит до внешнего действия. При невозможности записи ревизии внешнее действие вообще не вызывается.
- **Сбой после резервирования:** ревизия остаётся увеличенной, даже если внешнее действие не удалось. Это не полный откат, а консервативное инвалидирование старых CAS-снимков.
- **Непредсказуемые плагины MODX:** даже DB-процессор может вызвать событие, отправить письмо или записать файл; его внешний эффект не откатывается MySQL-транзакцией.
- **В тестовой ветке 1.2.8 `_runtime_preconditions` обязательны.** В защищённом режиме для update_element/delete_element дополнительно требуется полный серверный отпечаток целевого элемента. В обычном режиме `read_set: []` допускается: это только защита общей ревизии MCP. Старые клиенты без CAS не могут выполнять запись.
- **`flock` защищает операции на одном узле/общем lock-файле.** Отдельные серверы с независимой файловой системой требуют распределённого механизма или DB-lock.

## Переоценка критических проверок по текущей тестовой ветке (22.11.2026)

Эта запись уточняет **исторические** формулировки выше, появившиеся до завершения защищённого CAS и v4 TLS CI. Для решений о релизе пользоваться статусами ниже и актуальными тестами, не считать прежнее «не проверено» продолжающимся фактом.

- **Доказано в изолированной 1.2.8:** Ed25519 permit с отдельным публичным ключом, защитой от повторного nonce и fail-closed диспетчером; оба MODX; HTTPS endpoint, токен, signed mutations, replay и независимый readback; тесты `_build/test.ci-protected-auth.php` и `_build/test.ci-protected-http.py`.
- **Доказано для защищённых ресурсов:** полный target fingerprint из `get_site_state.read_set` требуется для `update_element` / `delete_element`; независимая Manager-запись при неизменной MCP-ревизии отвергается, как и перекрывающаяся транзакция Manager с удержанием InnoDB row lock. Маркеры тестов: `PROTECTED_CAS_MANAGER_EDIT_CONFLICT_DENIED_OK`, `PROTECTED_CAS_INNODB_ROW_RACE_DENIED_OK`.
- **Доказано для конкретного E2E:** актуальный коммит `817b418` — публичная матрица [12/12](https://github.com/rumata-estor/modx3-mcp/actions/runs/45008665939), приватная связка Controller/Executor → real TLS → disposable MODX [3/3](https://github.com/rumata-estor/site-agent-runtime/actions/runs/45008844831). В публичный CI не импортируются приватные ключи или закрытый Site Agent.
- **Остаётся релизным ограничением:** `read_set: []` допустим в незашищённом режиме для остальных действий; при изменениях не через MCP общий `site_revision` не обновляется. Надо задать и испытать target-fingerprint политику для каждого опасного mutator, не только ресурсов в protected mode.
- **Остаётся релизным ограничением:** полный внешнеподтверждённый сценарий человека/Telegram Bot API, production TLS/WAF/systemd, межузловое восстановление, плагины с внешними эффектами, сторонние процессоры и 94 неполно покрытых бизнес-действия. Успешные CI не означают атомарный откат чужих эффектов.

## CAS в управлении доступом — этап 1 PR #65

В тестовой 1.2.8 защищённые `update_user`, `delete_user`, `update_user_group`, `delete_user_group`, `update_role`, `delete_role` требуют **точный полный target fingerprint** (числовой ID) из `get_site_state.read_set`. Отпечаток связывает публично читаемые атрибуты с данными профиля и внутренними хешами секретов пользователя; клиент получает только 64-символьный итоговый SHA-256, а не значения секретов.

Интеграционный тест `_build/test.ci-acl-manager-conflict.php` в изолированных MODX2/3 проверяет внешние изменения в отдельном процессе MODX Manager для пользователя, группы и роли: `site_revision` остаётся прежней, устаревшие **update и delete** через MCP возвращают `STALE_STATE`, значение Manager и сам объект сохраняются. Все шесть действий получили сценарий `manager_out_of_band_edit_stale_target_denied` в машинном реестре; это только доказательство конкретного отказа, не атомарности внешних эффектов. Проверка с подписанным Ed25519-разрешением отдельно отвергает операции без полного снимка цели. Положительные CRUD-операции уже тестируются в `_build/test.ci-functional-acceptance.php`.

**Не считать этапом 2:** гранты, членство в группах, индивидуальные ACL-записи и массовые изменения правил пока не получили аналогичный полный target fingerprint. Эти операции всё ещё могут зависеть только от MCP `site_revision`; дальнейшие тесты должны учесть внешний Manager и конкурентные записи.

## P0: конкурентная запись членства обходит CAS группы — подтверждено (22.11.2026)

**Статус: OPEN / воспроизведённый security blocker.** В отдельном [PR #67](https://github.com/rumata-estor/modx3-mcp/pull/67) отпечаток `user_group` был расширен списком `modUserGroupMember`, что обнаруживает **последовательное** изменение состава группы независимым Manager-процессом; соответствующая одноразовая матрица прошла [12/12](https://github.com/rumata-estor/modx3-mcp/actions/runs/45013909441).

Но adversarial-сценарий подтвердил **TOCTOU**: независимый процесс Manager записывает новое членство в незавершённой InnoDB-транзакции; MCP успевает прочитать старый состав и выполнить `update_user_group` со старым отпечатком. После коммита Manager зафиксировано `ACL_MEMBERSHIP_TOCTOU_RACE_REPRODUCED`. Это происходит на MODX 2 и 3; [прогон с преднамеренно красным security-gate (12/12 заданий не прошли)](https://github.com/rumata-estor/modx3-mcp/actions/runs/45014060027). Такой тест не является общим отказом API — он намеренно запрещает объявлять систему безопасной при успешном обходе CAS.

**Причина:** межпроцессный `flock` синхронизирует только MCP; Manager его не соблюдает. Чтение связанных строк без транзакционных блокировок InnoDB не защищает от чужого незавершённого коммита. Кроме того, у ACL processor могут быть кэшевые/внешние эффекты, поэтому слепое добавление транзакции или `FOR UPDATE` без проверки атомарности и MODX 2/3 недопустимо.

**Критерии закрытия:** независимые Manager-вставка, обновление роли участника и удаление членства в перекрывающихся транзакциях; гарантированное обнаружение конфликта ДО запуска ACL processor; отсутствие выданного/утраченного разрешения после отказа; сохранение неизменённого `site_revision` при отказе и проверка readback; вся MODX 2/3 матрица зелёная. Дополнительно проверить, как блокировки защищают отсутствие строки (phantom) и работают при обычном уровне изоляции.

**Решение по интеграции:** PR #67 не объединять в основную 1.2.8 до выполнения критериев. Уже принятые PR #65/#66 для пользователя, роли и группы остаются, однако сами по себе не гарантируют сохранность конкурентного ACL-членства. Production, `main` и стабильную 1.2.7 не изменять.

## Дисциплина изменения

- Оригинальный коммит AgelxNash и его авторство не переписывать.
- Новые исправления и тесты фиксировать отдельными коммитами с указанием их назначения.
- Для любого расширения реестра мутирующих инструментов CI требует явной классификации CAS и обновления матрицы проверок.
- Нельзя заменять операцию через MODX MCP непосредственным SQL/HTTP/файлами на настоящем сайте. В CI временный SQL-триггер — только инструмент сбоя.
- Каждый заявленный результат должен иметь ссылку на конкретный workflow run и маркер результата, а каждый недоказанный инвариант — открытую запись в рисках.


## Дополнительные ACL-проверки (22 ноября 2026)

В изолированной ветке `feature/1.2.8-cas-pr46-20261121` выполнены следующие новые проверки безопасности:

- **`create_role`, `update_role`, `delete_role`:** создание случайной тестовой роли, чтение через MCP, обновление, проверка отказа по старому `site_revision`, удаление только своего тестового объекта. Прогон `44990530599` — 12/12 успешно.
- **`update_user_group`:** изменение имени собственной временной группы, чтение через MCP, отказ устаревшего CAS. Прогон `44990643863` — 12/12 успешно. Создание и удаление группы также входят в базовую приёмку.
- **Все 29 ACL:** отрицательные автономные тесты отказа процессора и полного отсутствия ответа, без утечки текста и без ложного сообщения об откате; отсутствие ответа теперь означает `MUTATION_OUTCOME_UNCERTAIN` (коммит `466fe1e`).
- **Все ACL-результаты:** безопасное маскирование вложенных credential-полей, включая успешный ответ `update_user`; автономный тест `_build/test.processor-secret-redaction.php` (коммит `95bf3e2`).

**Границы доказательства:** для большинства ACL-действий нет полного индивидуального позитивного сценария, fault-injection после частичного выполнения, независимого восстановления или тестов на межузловые гонки. Число 94 в машинном реестре отражает именно неразмеченное индивидуальное покрытие; не уменьшать его автоматически на основании общего CI. Релиз и production-установку не разрешать только по факту успешной матрицы.

## Защита статических файлов: следующий шаг

В коммите `788272e` проверка фактического места записи распространена с TV на все типы `make_static`: chunk, snippet, template, plugin, TV. Запрещены каталоги элементов через симлинк наружу и подмена самого корня `core/elements` (при этом штатный символический путь к `core_path` допустим, если итоговый `elements` находится непосредственно внутри реального корня). Автономные тесты подтверждают отказ до записи и корректный обычный `make_static`. [CI SUCCESS](https://github.com/rumata-estor/modx3-mcp/actions/runs/44998221948), [интеграционная матрица 12/12](https://github.com/rumata-estor/modx3-mcp/actions/runs/44998218560).

**Сохраняющийся риск:** проверка существующего пути и последующая запись — две отдельные файловые операции; от враждебной конкурентной подмены симлинка между ними (TOCTOU) этот контракт сам по себе не защищает. Кроме того, запись файла предшествует сохранению метаданных элемента, поэтому отказ позднего `save()` способен оставить частичный внешний эффект. Эти сценарии требуют отдельной модели отказов и безопасного восстановления.

**Аварийный отказ после записи файла:** начиная с `cb9877a`, если `make_static` записал файл, но последующий `element->save()` вернул отказ, ответ помечен `MUTATION_OUTCOME_UNCERTAIN` (не обещается откат файла). Самостоятельная fault-injection фикстура `_build/test.make-static-symlink-boundary.php` подтверждает, что файл остаётся на диске, а статус ясно предупреждает о неопределённом состоянии; при таком отказе обязательны независимое чтение MODX через MCP и проверка файла перед любым повтором.

Чтобы отделить существовавшее частичное покрытие от новых доказательств, добавлен отдельный disposable-тест `_build/test.ci-cas-acl-create-evidence.php` для `create_user_group` и `create_role`: точные CAS-предусловия, создание, независимое чтение, увеличение ревизии, отказ старого CAS, отсутствие повторной записи/дублирования, контроль после отказа и уборка через MCP. **Этот сценарий не доказывает отсутствие гонки с внешним MODX Manager и откат сторонних эффектов**. Такие риски остаются отдельно.
