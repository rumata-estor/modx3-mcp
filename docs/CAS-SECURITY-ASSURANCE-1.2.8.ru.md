## Воспроизводимые доказательства

Тестируются одноразовые MODX 2.8.9/PHP 7.4, MODX 2.8.9/PHP 8.2 и MODX 3.2.4/PHP 8.2 с MariaDB 10.11.

1. **TV/транзакция:** raw TV и `@INHERIT`, stale read set, два одновременных PHP-процесса (ровно один победитель), принудительный отказ обновления `site_revision` с откатом обеих TV. Восстановление по новой ревизии через MCP. Сценарии `_build/test.ci-pr46-tv-cas.php`, `_build/test.ci-pr46-cas-worker.php`, `_build/test.ci-pr46-mcp-readback.php`.
2. **Другие DB-операции:** десять сценариев с принудительным отказом ревизии, независимое чтение результата и уборка через `modxMCP::processRequest()`. Сценарий `_build/test.ci-cas-other-mutations.php`. Для `update_element_property` необходим отдельный сценарий с подготовленным свойством.
3. **Внешние эффекты:** шесть файловых/папочных команд запрещаются до выполнения при отказе ревизии. Проверяются штатные положительные операции и независимое чтение через MCP; после ошибки уже начатого действия ревизия остаётся увеличенной (консервативное состояние). Два реальных PHP-процесса с одинаковым снимком обновляют файл: один выполняется, второй получает `STALE_STATE`.
4. **Критические операции:** запрет до запуска `install_package`, `uninstall_package`, `run_processor`, `regenerate_token`, `empty_recycle_bin`. Реальная установка или удаление пакета в CI не производится.
5. **Полный каталог ранних отказов:** 104 зарегистрированных нетранзакционных действия: 104 отказа ревизии, 0 неожиданных исполнений, 0 пропусков на каждом из трёх MODX. Сценарий `_build/test.ci-cas-mutation-gates.php`.
6. **Пути медиафайлов:** 21 синтаксический тест и шесть сценариев через MCP отвергают traversal (`../`), недопустимые имена и управляющие символы. Нормальные операции продолжают работать.

[Прогон всех 104 gate-проверок и конкурентных файловых операций](https://github.com/rumata-estor/modx3-mcp/actions/runs/44930600618); [проверка path traversal](https://github.com/rumata-estor/modx3-mcp/actions/runs/44931045256).

Во всех тестах обычные действия над сайтами, ресурсами, TV, файлами, категориями и настройками идут **только через MODX MCP**. Единственное прямое обращение к SQL — установка/удаление специально подготовленного временного триггера MariaDB для имитации отказа. Это делается только в одноразовых средах GitHub Actions; тесты отказываются работать вне них.

## Семантика ошибок — не путать

- **DB атомарность:** транзакция успешно фиксирует и данные, и `site_revision`, либо откатывает оба изменения. Это относится только к покрытому набору DB-мутаторов, при поддержке транзакций таблицами и одним DB-подключением.
- **External revision reservation:** запись новой ревизии происходит до внешнего действия. При невозможности записи ревизии внешнее действие вообще не вызывается.
- **Сбой после резервирования:** ревизия остаётся увеличенной, даже если внешнее действие не удалось. Это не полный откат, а консервативное инвалидирование старых CAS-снимков.
- **Непредсказуемые плагины MODX:** даже DB-процессор может вызвать событие, отправить письмо или записать файл; его внешний эффект не откатывается MySQL-транзакцией.
- **В тестовой ветке 1.2.8 `_runtime_preconditions` обязательны.** В защищённом режиме для update_element/delete_element дополнительно требуется полный серверный отпечаток целевого элемента. В обычном режиме `read_set: []` допускается: это только защита общей ревизии MCP. Старые клиенты без CAS не могут выполнять запись.
- **`flock` защищает операции на одном узле/общем lock-файле.** Отдельные серверы с независимой файловой системой требуют распределённого механизма или DB-lock.

## Дисциплина изменения

- Оригинальный коммит AgelxNash и его авторство не переписывать.
- Новые исправления и тесты фиксировать отдельными коммитами с указанием их назначения.
- Для любого расширения реестра мутирующих инструментов CI требует явной классификации CAS и обновления матрицы проверок.
- Нельзя заменять операцию через MODX MCP непосредственным SQL/HTTP/файлами на настоящем сайте. В CI временный SQL-триггер — только инструмент сбоя.
- Каждый заявленный результат должен иметь ссылку на конкретный workflow run и маркер результата, а каждый недоказанный инвариант — открытую запись в рисках.

Прохождение 12/12 не утверждает абсолютную безопасность.

## Защита статических файлов: следующий шаг

В коммите `788272e` проверка фактического места записи распространена с TV на все типы `make_static`: chunk, snippet, template, plugin, TV. Запрещены каталоги элементов через симлинк наружу и подмена самого корня `core/elements` (при этом штатный символический путь к `core_path` допустим, если итоговый `elements` находится непосредственно внутри реального корня). Автономные тесты подтверждают отказ до записи и корректный обычный `make_static`. [CI SUCCESS](https://github.com/rumata-estor/modx3-mcp/actions/runs/44998221948), [интеграционная матрица 12/12](https://github.com/rumata-estor/modx3-mcp/actions/runs/44998218560).

**Сохраняющийся риск:** проверка существующего пути и последующая запись — две отдельные файловые операции; от враждебной конкурентной подмены симлинка между ними (TOCTOU) этот контракт сам по себе не защищает. Кроме того, запись файла предшествует сохранению метаданных элемента, поэтому отказ позднего `save()` способен оставить частичный внешний эффект. Эти сценарии требуют отдельной модели отказов и безопасного восстановления.

**Аварийный отказ после записи файла:** начиная с `cb9877a`, если `make_static` записал файл, но последующий `element->save()` вернул отказ, ответ помечен `MUTATION_OUTCOME_UNCERTAIN` (не обещается откат файла). Самостоятельная fault-injection фикстура `_build/test.make-static-symlink-boundary.php` подтверждает, что файл остаётся на диске, а статус ясно предупреждает о неопределённом состоянии; при таком отказе обязательны независимое чтение MODX через MCP и проверка файла перед любым повтором.

## Аварийные файловые сценарии и конкурентная запись (22.11.2026)

- `a0c07fa`: после изменения статического файла неуспешный процессор MODX сигнализирует `MUTATION_OUTCOME_UNCERTAIN`. В `_build/test.static-content-postwrite-fault.php` процессор искусственно отказывает после изменения файла; доказаны факт файлового изменения и отсутствие ложного утверждения об откате. Для нестатического элемента сохранён обычный `element save failed`.
- `26090d9`: оба маршрута записи сравнивают количество реально записанных байтов с длиной содержимого. В `_build/test.static-short-write-fault.php` инструментальная подмена `file_put_contents()` записывает лишь 2 байта: возвращается `MUTATION_OUTCOME_UNCERTAIN`, последующие вызовы процессора/`save()` не выполняются.
- `f93ec7d`: `make_static(tv)` создаёт конечный файл через `fopen('xb')`, чтобы не перезаписать его, если другой процесс занял путь между первоначальной проверкой и созданием. `_build/test.tv-exclusive-create-race.php` искусственно создаёт конкурирующий файл непосредственно перед открытием и проверяет сохранность чужих байтов и отказ в изменении метаданных. Успешное создание по свободному пути также проверено.

**Оставшиеся границы:** `xb` защищает только конечное имя TV, но не закрывает подмену родительского каталога/симлинка между проверкой и файловой операцией. Для полной защиты от враждебного локального процесса потребуются возможности платформы для безопасного дескрипторного доступа к каталогам или отдельный доверенный файловый посредник. Аналогично не доказана атомарность групповых операций `replace_across` и внешних событий MODX. Не делать вывод «полный откат» на основании зелёной матрицы.

## Частичные исходы пакетных мутаций: replace_across и bulk_resources

- `74d4dc5`: `replace_across` учитывает число **попыток** записать элементы. Любое исключение после первой попытки теперь преобразуется в `MUTATION_OUTCOME_UNCERTAIN`, без раскрытия подробных ошибок процессора в ответе. Выполняется best-effort обновление кэша; оно не превращает результат в успешный. `_build/test.replace-across-partial-fault.php` проверяет 7 сценариев (включая отказ на первой/второй цели и сохранность dry-run/нормального режима).
- `9ecb132`: `bulk_resources` больше не скрывает отказ через `results[].status=error` при возврате успешного результата верхнего уровня. Ошибки изменения или удаления любой цели теперь маркируются `MUTATION_OUTCOME_UNCERTAIN`, после best-effort обновления кэша; пакет не продолжается после отказа. `_build/test.bulk-resources-partial-fault.php` проверяет 7 сценариев отказа, нормального выполнения и dry-run.

**Ограничения:** совместимость ответов при частичных отказах намеренно изменена на fail-closed; успешные и dry-run ответы не менялись. Неизвестный ID по-прежнему выдаёт `not_found` без мутации. Существующая общая DB-CAS транзакция **не гарантирует** отмену событий MODX, файлов или внешних эффектов. Эти автономные fault-injection тесты подтверждают правильную классификацию неопределённого исхода, но не доказывают полный откат или идемпотентность сторонних процессоров.

## Внешние MODX-процессоры и транспортные пакеты: обработка отказов

- `2782ffd`: `run_processor` отличает отказ **до** диспетчеризации (проверка главного переключателя и независимых полномочий) от исключения/отсутствия ответа **после** запуска процессора. Последние случаи маркируются `MUTATION_OUTCOME_UNCERTAIN`, без вывода сырого текста исключения, который мог содержать секреты. Тест `_build/test.processor-master-switch.php` симулирует отсутствие ответа, исключение с токеном, обычный успешный ответ и отказ gate до вызова.
- `748e192`: `install_package` маркирует неопределённым результатом исключения при `workspace/packages/rest/download` и `workspace/packages/install`, а также отсутствующий либо ошибочный ответ скачивания; `uninstall_package` аналогично обрабатывает исключение при удалении. В `_build/test.package-uncertain-result.php` тесты сбоя расширены с 2 до 6, включая контроль отсутствия утечки секретного текста и ложного успешного аудита.

**Ограничения:** независимая Ed25519-авторизация и запреты ProcessorAccessPolicy не менялись. Эти тесты проверяют только обработку отказов на уровне MCP и не означают, что сторонний транспортный пакет, его плагины или внешние побочные эффекты могут быть откатаны. Для безопасного повтора обязательно независимое чтение фактического состояния пакета и файлов через разрешённый маршрут MCP. На production ничего не устанавливали и не удаляли.

## Проверка всех целей bulk_resources до начала записи

- В `d9a594a` добавлена предварительная проверка существования **всех** ID в `bulk_resources` до первого изменения. Отсутствующая цель даёт `NOT_FOUND` без записи; исчезновение цели между preflight и исполнением (включая ситуацию после предыдущих успешных изменений) даёт `MUTATION_OUTCOME_UNCERTAIN`. Автономная фикстура проверяет оба случая; `_build/test.ci-functional-acceptance.php` на настоящих disposable MODX 2/3 проверяет смешанный набор ID и независимое отсутствие изменений в существующем ресурсе.
- В `c7004d5` недопустимые ID (нечисловые значения, 0, отрицательные, bool, массивы, смешанные строки) отклоняются до записи, а превышение `limit` больше не сокращает список незаметно. Фикстура `_build/test.bulk-resources-partial-fault.php` расширена до 17 проверок. `dry_run` сохраняет возможность сообщить `not_found` по отсутствующему объекту, не изменяя данные.

**Граница доказательства:** preflight проверяет существование целей, но не заменяет обязательных Ed25519/CAS и не гарантирует, что сторонний процесс не изменит объекты после проверки. Ошибка после первой попытки записи считается неопределённым исходом. Состояние в production не менялось.
