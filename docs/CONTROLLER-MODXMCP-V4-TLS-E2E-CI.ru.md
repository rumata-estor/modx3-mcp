# MODX MCP 1.2.8 / Site Agent Controller v4 — полное HTTPS CI-испытание

**Статус:** сценарий расположен в отдельной ветке `feature/1.2.8-controller-tls-e2e-20261121`, ответвлённой от тестовой 1.2.8. Ничего не устанавливает на сайты и не меняет production, `main`, действующий Controller или тестовый runtime.

## Откуда берутся компоненты

- В каждом job закрытого GitHub Actions Site Agent устанавливается **с нуля** официальный MODX 2.8.9 (PHP 7.4, PHP 8.2) или MODX 3.2.4 (PHP 8.2). MariaDB — одноразовый контейнер.
- MODX MCP 1.2.8 берётся из открытой ветки по закреплённому коммиту и собирается штатным инсталлятором в этот MODX. Установочный пакет не публикуется и не выгружается на сайты.
- Site Agent Controller v4 и Executor v4 берутся из **закрытого репозитория** Site Agent по commit `364289feb1f5989fb35bfda1ace4fce0afc5c35c` и используются как импортируемые Python-модули, не как сервисы. **Сквозной запуск происходит в закрытом CI Site Agent**, где доступны эти исходники. Публичный CI MODX MCP не должен иметь токен для чтения Site Agent.
- Ключ Ed25519, API-токен MODX и сертификат OpenSSL используются только внутри изолированного job. Приватный ключ не копируется в MODX или в Git.

## Путь операции

1. Штатным MODX API Manager **только в CI** включаются проверка подписи Ed25519 и whitelist действий; тестовый узел доверяет TLS-завершению только от числового IP `127.0.0.1`.
2. PHP-сервер MODX слушает `127.0.0.1`. Локальный отдельный Python-процесс принимает **реальное TLS-соединение с действующим сертификатом на localhost** и передаёт его в MODX с доверенным `X-Forwarded-Proto: https`. Прямой HTTP без доверенного прокси остаётся запрещённым.
3. Временный **неопубликованный скрытый** ресурс создаётся через подписанный HTTP `create_element` самого MCP, затем независимо читается `get_element`.
4. Executor получает состояние `get_site_state` с полным fingerprint и ресурс через HTTP `get_element`. Controller создаёт замороженный запрос с CAS, фиктивный проверенный Relay **симулирует** доставку и человеческое утверждение (в CI не участвует реальный человек).
5. Controller выдаёт одноразовый Ed25519 permit, Executor проверяет подпись публичным ключом, неизменное содержимое, цель, CAS и реальный TLS и выполняет **ровно один** `update_element` через HTTP MCP.
6. Отдельный HTTP `get_element` подтверждает содержимое, Controller фиксирует `cas_verified`. Повтор точно того же HTTP-запроса/nonce должен получать отказ.
7. Аварийный тест на втором ресурсе: MCP **коммитит** update; TLS-прокси **теряет ответ после backend commit**. Executor должен выдать `needs_review` без повтора, а MCP — запретить воспроизведение потраченного nonce.
8. Обе временные страницы удаляются **через подписанный MCP `delete_element`** с новым CAS, не прямыми SQL-запросами. В конце job уничтожаются временная база, PHP-процесс, секреты и TLS-окружение.

## Ограничения безопасности и трактовки результата

- Это CI с одноразовыми тестовыми **виртуальными UID**: тестовые вызовы `ControlStore.handle(uid, ...)` моделируют Agent/Relay/Executor, а системный `SO_PEERCRED` действующих сервисов здесь не задействован. У Executor в CI подменяется только функция проверки настоящего Linux UID/GID, но проверка прав в Controller остаётся.
- Установщик безопасности и тестовый Node.js-подписант разрешены **только для создания/удаления временных ресурсов**. Основное изменение проверяется исключительно через human-reviewed Controller v4.
- TLS действительно работает между Executor и локальным тестовым прокси; между прокси и PHP используется loopback HTTP, как при TLS-терминации. Этот тест не доказывает безопасность внешней сетевой конфигурации или реальные сертификаты сайта.
- Не запускается Telegram и не подтверждается доставка настоящему человеку. Проверяются серверные инварианты согласования, а не пользовательский мессенджер.
- Нет автоматического разрешения записи в запущенном Site Agent. Флаги нового исходного Controller/Executor остаются выключенными для рабочих процессов.
- При неуспехе CI результаты не считают подтверждёнными. Каждый запуск должен показать отдельно успех MODX 2 / PHP 7.4, MODX 2 / PHP 8.2, MODX 3 / PHP 8.2.

Этот e2e-прогон дополняет локальные тесты CAS, replay, транзакций и TLS. Он не заменяет отдельного разрешения владельца на установку новой версии в тестовый runtime и последующую независимую проверку production.


**CI isolation (21.11.2026):** тестовый запуск из открытого репозитория MODX MCP не мог получить закрытый Site Agent (`Repository not found` у стандартного GITHUB_TOKEN). Это ожидаемая граница доступа, не основание делать репозиторий публичным. Сценарий запускается из закрытого CI Site Agent с публичным MODX MCP; права или секреты не расширяются.
