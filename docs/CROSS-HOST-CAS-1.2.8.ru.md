# Межсерверная конкуренция и аварийные блокировки — MODX MCP 1.2.8

**Статус: экспериментальное исправление в Draft PR #164, не релиз/production.**
Не требует Site Agent, внешнего демона, отдельной таблицы или Python.

## Подтверждённая проблема

Раньше `StateSupport::withMutationLock()` удерживал только локальный `flock`.
Если два PHP-хоста используют разные каталоги кеша, такой lock не общий.
При двух одновременных изменениях с одним `observed_site_revision` оба
запроса успевали пройти проверку до записи ревизии.

**Красный доказательный тест:** [run 45127490103](https://github.com/rumata-estor/modx3-mcp/actions/runs/45127490103).
Во всех 12 disposable конфигурациях MODX 2/3 с PHP 7.4–8.4 два процесса
с разными локальными lock-файлами и общей MariaDB создали два разных чанка,
хотя обе команды использовали одну исходную CAS-ревизию.
Тест искусственно расширял окно гонки SQL-триггером `SLEEP(0.7)`;
триггер и чанки существуют **только в одноразовой CI-базе**.
Это воспроизводимая гонка, а не предположение.

## Минимальное исправление

`withMutationLock()` сохраняет локальный `flock`, после него на том же
подключении MODX получает именованный MySQL/MariaDB `GET_LOCK`.
Имя стабильно формируется из текущей схемы БД и таблицы системных настроек
(включая префикс MODX): разные узлы с одним writer получают одно имя.

- `GET_LOCK` должен подтвердить успех; ожидание ограничено 5 секундами.
- При недоступной/занятой БД или неподтверждённом получении lock операция
  останавливается с `CAS_LOCK_UNAVAILABLE` **до записи**.
- Подтверждённый lock удерживается на время CAS, MODX-процессора,
  транзакции и возможного внешнего эффекта данной команды.
- В `finally` требуется подтверждённый `RELEASE_LOCK`; при отказе
  результат помечается `MUTATION_OUTCOME_UNCERTAIN`, не ложным успехом.
- При SIGKILL или разрыве сеанса MySQL освобождает его автоматически;
  не вводим собственный timeout/lease/reconciliation-сервис и не
  повторяем автоматически спорную операцию.

**Зелёный первый тест после исправления:** [run 45127624824](https://github.com/rumata-estor/modx3-mcp/actions/runs/45127624824),
12/12 на MODX 2/3. В каждой конфигурации CAS дал одну запись и
`STALE_STATE` для проигравшего запроса. Реальный SIGKILL отдельного
PHP-процесса освободил именованную блокировку, отменил незакоммиченную
ревизию, второй процесс смог войти. Обычный CI также зелёный.
**Расширенная матрица 12/12 зелёных:** [run 45127992259](https://github.com/rumata-estor/modx3-mcp/actions/runs/45127992259).
Подтверждены same-target изменение одного чанка с одним fingerprint
(ровно один успех и один `STALE_STATE`), конечный тайм-аут `GET_LOCK`
с отказом до callback и освобождение после реального SIGKILL.

## Границы гарантий — обязательно

1. Тест использует **два отдельных PHP-процесса с разными локальными
   `cache_path`**, что моделирует два сервера. Это не физический
   multi-host, отдельные сети, балансировщики и PHP-FPM.
2. Защита распространяется только на узлы, использующие **общий writer
   MySQL/MariaDB и эту версию кода**. `GET_LOCK` не распределяется
   по независимым master-серверам, Galera multi-primary или
   некоординированным кластерам. Такие топологии требуют отдельной
   проверки/ограничения перед релизом.
3. Старый MCP 1.2.7 и ручные действия MODX Manager **не соблюдают** этот
   именованный lock. При rolling-upgrade нельзя считать смешанный пул
   защищённым; развертывание требует остановить записи, обновить все
   MCP-узлы и только затем возобновить работу.
4. Внешние скрипты, плагины, файловые операции, транспортные пакеты
   и соединения со сторонними сервисами не становятся транзакционными.
   `MUTATION_OUTCOME_UNCERTAIN` требует независимого readback и
   нового решения пользователя, а не автоматического replay.
5. На целевых хостингах проверить MySQL/MariaDB `GET_LOCK`, сетевые
   обрывы, сессионный pooling/reconnect и реальные PHP-FPM процессы.
   Отсутствие общей сессии с тем же DB writer — блокер.
6. Не путать разблокировку после смерти процесса с восстановлением
   прерванной задачи. Последнее относится к клиенту/Site Agent.

## Аварийный разрыв DB-сессии и deadlock (23.11.2026)

Дополнительная CI-фикстура: `_build/test.ci-db-session-faults.php`.
Она использует реальную одноразовую MariaDB и отдельные PHP-процессы.
`KILL CONNECTION` адресован **только своему CI-подключению**; для
deadlock создаётся отдельная случайная InnoDB-таблица, которая удаляется
после испытания. Содержимое штатных ресурсов сайта в этом тесте не
редактируется, кроме одного специально созданного временного чанка.

Проверяемые инварианты:

1. PHP начал транзакцию, зарезервировал ревизию, после чего другое CI-
   соединение выполнило `KILL CONNECTION`. Результат должен быть
   `MUTATION_OUTCOME_UNCERTAIN`, не успех и не безусловный rollback.
   Незакоммиченная ревизия должна отсутствовать при независимом чтении.
2. После потери сессии новый процесс должен получить `GET_LOCK` без
   ручного снятия блокировок; новый отдельно авторизованный запрос после
   свежего read/CAS проходит и не воспроизводит оборванную операцию.
3. В InnoDB создаётся реальный deadlock между транзакцией PHP/MCP и
   другой DB-сессией. Большая внешняя транзакция (много строк) делает
   жертвой меньшую транзакцию MCP. Silent `PDOStatement::execute()=false`
   не должен выдавать обычную ошибку или сырой SQL: исход неизвестен.
4. После deadlock общая блокировка должна освобождаться автоматически,
   независимый процесс может выполнить новую операцию.

**Промежуточное доказательство:** [run 45129727020](https://github.com/rumata-estor/modx3-mcp/actions/runs/45129727020)
(12/12 красных, ожидалось): обрыв соединения/подключение проходили,
но при гарантированной победе внешней транзакции над MCP
`execute()` вернул `false`; ошибка транзакции классифицировалась
обычной `row 2 lock failed` вместо `MUTATION_OUTCOME_UNCERTAIN`.
В PR #164 добавлено минимальное исправление: после ошибки внутри DB
транзакции наружу сохраняются только явные детерминированные отказы
CAS/авторизации/валидации **до эффектов**, все прочие ошибки (включая
непроверенный исход внешних эффектов) дают безопасный unknown.
**Исправление подтверждено:** [полная disposable-матрица 45130066617](https://github.com/rumata-estor/modx3-mcp/actions/runs/45130066617) **12/12**, а после добавления post-COMMIT disconnect
[полная матрица 45130314583](https://github.com/rumata-estor/modx3-mcp/actions/runs/45130314583) **12/12**, общий [CI 45130322482](https://github.com/rumata-estor/modx3-mcp/actions/runs/45130322482) зелёный.
После настоящего deadlock рабочая транзакция не маскирует ошибку под успех,
не раскрывает SQL и не делает автоматически повторную запись.

**Отдельная граница после COMMIT:** фикстура сначала фиксирует транзакцию
ревизии, затем другая сессия завершает её DB-подключение до освобождения
`GET_LOCK` и выдачи ответа. Независимое чтение подтверждает, что ревизия
**увеличилась**, тогда как MCP сообщает
`MUTATION_OUTCOME_UNCERTAIN`. Это доказывает защиту от ложного успеха
на указанной границе, но не атомарность произвольных внешних эффектов.

Для выпуска ещё требуются review, реальные отдельные хосты/PHP-FPM,
подтверждение схемы и подключения к одному writer и план upgrade 1.2.7→1.2.8.

**Граница:** этот тест не моделирует реальный сетевой балансировщик,
Galera/multi-primary, перенос MySQL-сессии через proxy, а также эффекты
произвольных PHP-плагинов после потери DB lock. Переход с 1.2.7 требует
отдельной координации всех узлов; независимое прочтение состояния и новое
решение пользователя остаются обязательными при unknown.
