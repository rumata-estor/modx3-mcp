# MODX MCP 1.2.8 — независимая авторизация по Ed25519 (подготовка)

**Текущий статус: защищённый режим реализован в тестовой ветке и прошёл интеграционные тесты на одноразовых MODX 2 и 3, но НЕ установлен на рабочие сайты и НЕ выпущен.** Обычный режим по умолчанию выключает независимую проверку подписи, но сохраняет обязательный CAS. Включение защищённого режима на действующих сайтах требует отдельной подготовки и разрешения.

## Модель доверия

- Внешний доверенный Controller подписывает конкретное разрешение своим приватным ключом Ed25519; секрет не попадает на сервер MODX.
- MODX MCP сохраняет только публичный ключ доверенного контроллера, привязанный к конкретной инсталляции. API-токен HTTP остаётся независимым первым уровнем аутентификации.
- Подписываемые поля имеют строго фиксированный порядок, версии и кодировку: audience, site_id, contour, action, element_type, SHA-256 точного HTTP-запроса, случайный nonce, issued_at и expires_at. Нельзя подменить имя операции, сайт или параметры.
- Сервер получает ожидаемую аудиторию, site_id, contour и публичный ключ из собственной защищённой конфигурации; доверять таким полям в теле запроса запрещено.
- Сначала сверяется идентичность клиента и криптографическая подпись, затем текущий CAS и полномочия; только после этого допускается выполнение.
- Сам по себе IndependentPermitV1::verifyCryptographicClaims — только офлайн-проверка подписи, не выдаёт право на изменение. Не подключать его к API напрямую.

## Предупреждение о старом эксперименте

В изолированной ветке защиты 2026-11-21 был формат permit на HMAC с одним секретным ключом у проверяющего и подписывающего. Он не обеспечивает желаемое разделение ключей; исходный эксперимент не переносился в 1.2.8. Авторизация старым HMAC/permit-v1 или v2 без явной миграции запрещена.

## Проверено

Файл _build/test.permit-ed25519-interop.cjs подписывает данные в изолированном Node.js, передаёт PHP только подпись, публичный ключ и поля, затем _build/test.permit-ed25519-verify.php проверяет 14 сценариев: действительная подпись, подделка подписи или публичного ключа, смена сайта/операции/типа/nonce/запроса, истечение/ранний срок действия, добавление/удаление поля, неподдерживаемая версия.

Тесты должны проходить на PHP 7.4/8.2 с ext-sodium. Если libsodium отсутствует — fail closed, без перехода на HMAC.

В CI дополнительно предусмотрен тест одноразовости на MariaDB: _build/test.ci-permit-nonce-ledger.php. Он создаёт и удаляет отдельную временную таблицу nonce, не изменяет данные сайта. Резервирование и воспроизведение nonce выполняются через внутренний авторизационный примитив, а не обходят бизнес-операции MCP. Наличие успешно проверенного примитива не означает, что он уже участвует в обработке HTTP-запросов.

## Что реализовано и подтверждено

1. **Ed25519 и независимое доверие.** MODX хранит только публичный ключ; приватный остаётся у внешнего подписанта. Подписанный permit привязан к audience/site/contour/action/type, точным байтам HTTP-запроса, nonce и сроку жизни.
2. **Одноразовость.** Отдельная автокоммитная InnoDB-таблица nonce; уникальный индекс. Два независимых PHP-процесса с одним nonce дают одного победителя, повтор запрещён даже после аварийного завершения процесса. Нельзя возвращать nonce обратно в пул.
3. **Единый диспетчер.** При external_authorization_required=1 разрешение проверяется внутри общего защищённого маршрута на MODX 2 и 3. Без permit, с неправильной подписью, без актуального CAS или при отключённом Runtime операция отклоняется.
4. **Самостоятельная политика сайта.** Настройка permit_allowed_actions задаёт точный CSV-список разрешённых действий. Значение по умолчанию пустое = **запрет всех мутаций**, даже с действительным permit. Отсутствие или повреждение режима авторизации — fail closed. Список и ключи не принимаются из запроса.
5. **HTTP.** Реальный путь assets/components/modxmcp/api.php, API-токен и X-ModxMCP-Permit проходят сквозные проверки Python и отдельным Node-клиентом на MODX 2/3. Возврат AUTH_DENIED — HTTP 403; отсутствие/неверный API-токен — HTTP 401.
6. **Целевой CAS.** В защищённом режиме update_element/delete_element требуют полный серверный fingerprint целевого элемента из get_site_state.read_set. Для обычного ресурса InnoDB FOR UPDATE защищает интервал между сравнением и записью от одновременного изменения администратором; тест включает настоящую перекрывающуюся транзакцию Manager.

Подтверждённые прогоны: [HTTP (Python + Node, 3/3)](https://github.com/rumata-estor/modx3-mcp/actions/runs/44936573138), [конфликт и настоящая гонка с MODX Manager (3/3)](https://github.com/rumata-estor/modx3-mcp/actions/runs/44937564770). Проверки привязаны к конкретным commit SHA; новые изменения требуют нового зелёного CI.

## Что остаётся до внедрения на сайты

- Нужна самостоятельная реализация **выдачи** Ed25519-разрешений в тестовом Controller/Executor и раздельная процедура хранения, ротации, отзыва и резервного восстановления доверенных ключей. Текущий CI-подписант не является готовым production-контроллером.
- Реальные TLS/CA-проверки и доверенные прокси не заменяются локальной эмуляцией HTTPS в CI.
- Для мутирующих команд кроме update_element/delete_element и TV не все целевые состояния проверяются собственным fingerprint; проверки 116 gate-отказов **не доказывают** безопасность всех бизнес-операций при частичных ошибках.
- Нужно проверить особые драйверы файлов, пакеты, плагины, ACL/пользователей, межузловую конкурентную работу. Для них могут потребоваться отдельные permits и процедуры восстановления.
- Нужен контролируемый rollout из 1.2.7: старые клиенты без CAS перестанут изменять сайты. Без миграции клиентов включать обновление нельзя.
- Настройки безопасности и таблицу nonce нужно создавать отдельно, при явном административном согласии. Обычный транспорт **не** включает защищённый режим и **не** генерирует приватный ключ.

До завершения этих пунктов тестовую ветку нельзя сливать в main, публиковать в качестве релиза или устанавливать на действующих сайтах.
