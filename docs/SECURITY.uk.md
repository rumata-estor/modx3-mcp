# MODX MCP — безпека та модель довіри

[English](SECURITY.md) · [Русский](SECURITY.ru.md) · [Español](SECURITY.es.md) · [Deutsch](SECURITY.de.md) · [Français](SECURITY.fr.md) · [Українська](SECURITY.uk.md) · [Қазақша](SECURITY.kk.md) · [Nederlands](SECURITY.nl.md) · [Polski](SECURITY.pl.md) · [Встановлення](INSTALL.uk.md) · [Можливості](CAPABILITIES.uk.md) · [API](API.uk.md)

Цей посібник описує межу довіри публічного **MODX MCP 1.2.5**, його налаштування безпеки та важливі обмеження. Він не описує жодної зовнішньої інфраструктури керування агентами.

## Головне правило

**Ставтеся до токена API MODX MCP як до адміністративних облікових даних.** Саме лише знання URL кінцевої точки або задокументованих назв інструментів не авторизує запит. Проте дійсний `X-MCP-Token` може дозволити широкі зміни сайту.

Після автентифікації запиту сервер вибирає службовий обліковий запис із правами MODX **`sudo`**. `modxmcp.service_user_id` може вказувати активний обліковий запис `sudo`; за замовчуванням, коли значення дорівнює нулю, вибирається перший активний користувач `sudo`. Це **не** авторизація кожного зовнішнього користувача на основі індивідуальних дозволів оператора в менеджері.

Власник токена потенційно може змінювати сніпети, плагіни, шаблони, ресурси, налаштування та інший чутливий вміст. Редагування PHP у виконуваних елементах MODX може призвести до виконання довільного PHP-коду з привілеями процесу вебзастосунку.

## Захист кінцевої точки PHP

| Засіб контролю | Поведінка та обмеження |
| --- | --- |
| Токен | Потрібен `X-MCP-Token`; перевіряється на відповідність налаштуванню `modxmcp.api_token`. |
| HTTPS | `modxmcp.require_https` увімкнено за замовчуванням; перевірте конфігурацію завершення TLS. |
| Список дозволених IP-адрес | `modxmcp.allowed_ips` зіставляє `REMOTE_ADDR` із точними IP-адресами або діапазонами IPv4 CIDR; порожнє значення дозволяє будь-яку адресу вузла, що підключається. |
| Зворотний проксі | `modxmcp.trust_proxy_https` вимкнено за замовчуванням; вмикайте лише за довіреного, правильно налаштованого зворотного проксі. |
| Головний перемикач | Вимкнене `modxmcp.enabled` забороняє автентифіковані операції API. |
| Обмеження розміру | `modxmcp.max_payload_bytes` обмежує розмір вхідних даних JSON. |
| Прямий доступ до процесорів | `modxmcp.allow_run_processor` вимкнено за замовчуванням. |
| Групи можливостей | `modxmcp.disabled_groups` вимикає вибрані сімейства інструментів. |

**Вимкнені сімейства інструментів не є повноцінною межею авторизації.** Стандартні інструменти створення, оновлення та видалення системних налаштувань відхиляють ключі, що починаються з `modxmcp.`, зокрема спроби перейменувати інші налаштування з додаванням цього префікса. Ротація токена залишається окремою привілейованою дією. Це не ізольоване середовище: автентифікований викликач, який може редагувати виконуваний PHP (або викликати явно дозволені процесори), усе одно може впливати на безпеку сайту. Для різних операторів потрібні незалежні серверні засоби авторизації.

Правильна автентифікація кінцевої точки не означає наявності вбудованого обмеження частоти запитів. Якщо вашому розгортанню потрібні такі обмеження, застосуйте їх на рівні зворотного проксі або вебсервера.

## Стандартний MCP-клієнт Node.js і прямі HTTP-виклики

Клієнт Node.js, що постачається з проєктом, має додаткові запобіжники для деяких змін: резервні копії певних об’єктів перед зміною, явний дозвіл ризикованих операцій через змінні середовища та координацію викликів. **Власні клієнти, які надсилають POST безпосередньо до `api.php`, не виконують цих клієнтських захисних процедур.**

Сервер PHP також реалізує блокування та перевірки передумов для деяких змін, а також записи аудиту. Це не робить прямий HTTP-доступ рівнозначним використанню стандартного MCP-клієнта.

Якщо ви створюєте власну HTTP-інтеграцію, реалізуйте власні резервні копії, авторизацію, підтвердження та процедури відновлення.

## Рекомендована конфігурація production

1. Використовуйте HTTPS із дійсним сертифікатом.
2. Зберігайте токен у захищеній конфігурації клієнта або менеджері секретів. Ніколи не додавайте його до URL, публічного коду, знімків екрана, звернень до підтримки чи журналів.
3. За можливості обмежте доступ до кінцевої точки відомими IP-адресами клієнтів або захищеною мережею/проксі. Перевірте, яку адресу PHP фактично бачить у `REMOTE_ADDR`.
4. Залишайте `modxmcp.allow_run_processor = 0`, якщо немає конкретної потреби.
5. Вимкніть невикористовувані групи можливостей, пам’ятаючи, що це не індивідуальний контроль доступу користувачів.
6. Залишайте `modxmcp.debug` вимкненим у production.
7. Підтримуйте незалежні, перевірені резервні копії сайту MODX і бази даних.
8. Використовуйте `dry_run` у деструктивних масових інструментах, коли він доступний; вручну підтверджуйте зміни коду, дозволів і налаштувань зі значним впливом.
9. Виконайте ротацію токена API за підозри на компрометацію; негайно оновіть конфігурацію кожного авторизованого клієнта.

## Секрети та приватна інформація у відповідях інструментів

`modx_list_system_settings` і `modx_get_system_setting` можуть повертати значення, що містять **токени API та інші секрети**. Не передавайте повні результати до публічних журналів, звітів про проблеми, аналітичних конвеєрів або зовнішньої моделі без оцінки ризику для конфіденційності.

Прочитані файли, журнали помилок, записи користувачів і дані замовлень інтернет-магазину також можуть містити приватну або чутливу інформацію.

## Межі захисту

Документація не може запобігти неправильному розумінню запиту ШІ-клієнтом. Одне редагування спільного сніпета, плагіна або шаблону може вплинути на кілька сторінок. Будь-який застосунок, що надає різні права кільком операторам, має забезпечувати ці права в межах своєї довіреної серверної частини, а не лише інструкціями в запиті чи прихованим списком інструментів.

Якщо ви виявили вразливість, не публікуйте робочі облікові дані чи дані клієнтів у публічному GitHub issue. Відкличте розкриті секрети та надайте достатньо очищеної від чутливих даних інформації, щоб супроводжувачі могли безпечно відтворити проблему.

## Конкурентні зміни TV ресурсів і CAS v2

Починаючи з опублікованого транспортного пакета 1.2.3 для MODX 2 і MODX 3, `get_site_state` повідомляє `precondition_version=2` для CAS значень TV на боці Connector. Захищений запит `modx_update_resource_tvs` містить керовані Runtime `_runtime_preconditions`: спостережену ревізію сайту, суворе дотримання ревізії та мапу `expected_tvs` із точним набором назв TV, що змінюються. Connector перевіряє ці умови під своїм блокуванням змін сайту та відхиляє застарілі значення замість їх непомітного перезаписування.

**Обмеження:** базова схема MCP не вимагає цього внутрішнього захисту, тому незахищений прямий виклик **не можна** представляти як безпечний за одночасної роботи агентів. Користувачі Site Agent мають застосовувати перевірений шлях Runtime `modx-tv-change` або Executor. Після невдалого виклику CAS потрібні свіже читання й новий план, а не сліпі повторні спроби.
