# MODX MCP 1.2.8 — независимый аудит безопасности системных настроек

**Статус:** отдельная тестовая ветка. Никаких изменений на production.

## Подтверждённые существующие защиты

- `ProtectedSettingsGuard::assertMutableKey()` запрещает любые ключи
  `modxmcp.*` в `create/update/delete_system_setting`, включая изменение
  по исходному/новому ключу, trim/case, update по ID (если применим).
- `ProcessorAccessPolicy` запрещает универсальные setting-процессоры
  и непрозрачный `context/update`, включая привилегированный режим.
- `ProcessorMutationTool` блокирует защищённые context settings и
  сторонние процессоры, способные менять доверенные настройки.
- Подпись Ed25519 проверяется независимо от CAS, а политика при protected
  mode читается непосредственно из таблицы настроек, не из устаревшего cache.

## Дополнительная обнаруженная проблема чтения

`SystemSettingListTool::normalize()` скрывал распространённые токены,
но пропускал часть camelCase и нестандартных имён (например,
`vendorAuthToken`). `ClientConfigSupport::normalize()` возвращал
`value`, `default` и `context_values` без маскирования по ключу.
`ContextSettingGet/ListTool` возвращали результат processor без
контекстного редактирования значений.

Исправление `SettingSecretSupport` разделяет общую политику сокрытия
значений по *имени настройки*, а не по имени поля `value`.
В ClientConfig скрываются global, default и контекстные переопределения.
Для контекстных processor outputs обрабатываются `object`, `results`
и одиночные значения. Обычные настройки и публичный ключ проверки
подписи `modxmcp.permit_public_key` не скрываются.

**Ограничение:** эвристика имён не распознает секрет, сохранённый под
невыразительным ключом `custom_data`. Такой ключ нельзя считать
безопасным по умолчанию: администратор должен понимать ограничения и
не хранить credentials под нехарактерными именами.

## Испытания

- `_build/test.security-settings-immutability.php`: запрет
  create/update/rename/delete `modxmcp.*`, включая нормализацию.
- `_build/test.setting-secret-boundaries.php`: unit-сценарии
  системных, ClientConfig, контекстных secret values и обычных ключей.
- `_build/test.ci-settings-read-redaction.php`: одноразовый
  MODX 2/3, создаёт фиктивные настройки через Manager API,
  проверяет `get/list_system_settings` через MCP,
  затем удаляет фикстуры. Проверяет запрет изменения trust anchor
  через штатный MCP. Реальных секретов не использует.
- Существующие protected HTTP/Ed25519/processor проверки остаются
  обязательными.

## Перед релизом

- Проверить сторонние ClientConfig-инсталляции с секретными значениями;
  не принимать скрытый secret обратно как новое значение при save.
- Проверить `get_context_setting` и `list_context_settings` на
  реальных MODX 2 и 3 для вложенных структур ответа processor.
- Регрессионно проверить показ обычных настроек и публичных ключей.
- Сравнить работающий 1.2.7 и тестовую 1.2.8; изменение режима
  чтения секретов явно указать в release notes.

**Не смешивать** подтверждённые тесты запрета мутаций с гарантией
безопасности всех сторонних процессов, HTTP endpoint и UI.
