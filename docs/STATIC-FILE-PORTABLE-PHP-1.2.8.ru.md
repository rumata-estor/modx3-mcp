# Static files: переносимое усиление без Python — MODX MCP 1.2.8

**Статус:** изолированный кандидат для тестовой ветки, без изменений production.

## Цель и ограничения

В отличие от экспериментального PR #95, новое решение использует только
штатный PHP — без `/usr/bin/python3`, `proc_open`, FFI, Node.js или
других обязательных runtime-зависимостей. Не меняет процесс установки MODX.

**Ограничение безопасности:** PHP без нативных `openat()`/`O_NOFOLLOW`
не способен гарантированно защитить *каждое* обращение при произвольной
конкурентной замене родительского каталога злоумышленником, уже имеющим
право записывать в файловую систему с привилегиями PHP. Не утверждаем
полное устранение TOCTOU при такой модели угроз.

## Изменение

- `StaticFileWriteSupport::replace()`: создаёт случайный временный файл
  через `fopen('xb')` **в каталоге назначения**, записывает все байты,
  проверяет результат, сохраняет режим доступа и только затем
  выполняет `rename()` поверх оригинала.
- Старый файл не усекается на этапе записи; при ошибке временного
  файла оригинал сохраняется.
- Существующая проверка сохранённых путей, симлинков и hard links
  остаётся обязательной; перед заменой повторно сверяются
  идентификаторы директории и целевого файла.
- TV `make_static` сохраняет штатный `fopen('xb')` —
  **атомарный запрет создания, если конечный TV-файл занят**.
- Ошибки после начала файлового действия остаются
  `MUTATION_OUTCOME_UNCERTAIN`; автоматических повторов нет.

## Совместимость и дополнительные риски

- Нужна возможность **создавать временный файл и выполнять rename
  в каталоге назначения**. На некоторых хостингах PHP может иметь
  право изменять отдельный файл, но не создавать записи в его каталоге.
  Это повод проверить конкретный хостинг до релиза.
- Временный файл принадлежит текущему PHP-пользователю. Если оригинал
  принадлежит другому системному пользователю, последующая смена
  владельца при rename может изменить работу внешних процессов.
- Режим доступа оригинала сохраняется; права нового файла
  устанавливаются с учётом `umask`.
- Обычная атомарность `rename()` предполагает локальную совместимую
  файловую систему; сетевые/distributed FS и Windows требуют
  дополнительных проверок.
- Одновременные обновления статического файла из MODX Manager
  и через MCP всё ещё требуют CAS и независимой сверки состояния.
- Это **не** средство защиты от вредоносного PHP-кода, который уже
  работает с теми же правами на файлы и каталоги.

## Тестирование

`_build/test.static-portable-replace.php`: настоящая запись бинарных
данных, обновление, сохранение прав, запрет hard links и симлинков,
атомарность создания и отсутствие временных остатков.

`_build/test.static-short-write-fault.php`: ошибка *временной*
записи не повреждает старый файл; не выполняется последующее
сохранение MODX-метаданных.

`_build/test.ci-static-portable-write.php`: только disposable CI,
проверка установленного компонента на MODX 2 и MODX 3.

**Решение для релиза:** прежде чем принимать код в main,
проверить сценарии обновления 1.2.7 → 1.2.8 и ограничения на создание
файлов, владельцев и `rename` на целевых хостингах. При отсутствии
гарантированной совместимости оставить эту реализацию в тестовой
ветке; не делать обязательным новый режим, который ломает работу сайта.
