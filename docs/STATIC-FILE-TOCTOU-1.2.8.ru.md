# Статические файлы: защита от TOCTOU — тестовая 1.2.8

**Статус:** изолированный кандидат; не выкатывать на production без проверки
совместимости целевого хостинга и принятия решения по зависимостям.

## Угроза

Повторный `realpath()` перед `file_put_contents()` не обеспечивает
атомарности: другой процесс способен заменить вложенный каталог
`core/elements/chunks` симлинком на внешний каталог **после** проверки.
Даже запрет hard links не устраняет эту гонку.

## Реализация

`StaticFileIoSupport.php` вызывает `Security/static_io_guard.py`
через `proc_open` **без оболочки**. Помощник использует `os.open` с
`dir_fd`, `O_DIRECTORY`, `O_NOFOLLOW`, `O_CLOEXEC` для каждого каталога,
затем открывает конечный файл без следования по симлинку. Проверяет,
что конечный inode — обычный файл с `nlink=1`. Усечение происходит
**после открытия и проверки** дескриптора, поэтому подмена имени файла
не способна перенаправить уже открытый дескриптор. Создание TV использует
атомарное `O_CREAT|O_EXCL`.

Внешний путь ядра определяется по `realpath(core_path)`; внутри него
помощник принимает только `elements/…`. Не допускает `..`, пустые
компоненты и дополнительную глубину/длину сверх ограничений. Не
выполняет shell-команды с вводом пользователя.

**Нет небезопасного fallback.** Если `/usr/bin/python3`, `proc_open`
или файл помощника отсутствуют, обработка статического файла
завершается отказом. Это изменение требований к окружению:

- Linux/Unix с поддержкой `openat`-подобных операций Python `dir_fd`.
- Python 3 по пути `/usr/bin/python3`.
- Разрешённый `proc_open` для PHP-процесса, включая PHP-FPM.
- Права на файл помощника и каталог компонента, исключающие изменение
  кода недоверенным пользователем.

Для обычных MODX-сайтов, где `proc_open` запрещён, операции
`make_static`, `edit_element_lines` и другие записи содержимого
статических элементов через MCP теперь будут отвергаться.
**Нельзя незаметно включать в релиз до проверки совместимости.**

## Доказательства

- `_build/test.static-toctou-race.py`: конкурентные подмены вложенного
  каталога симлинком на внешний, 500 попыток ввода-вывода; внешний
  файл обязан оставаться неизменным, часть попыток обязана получать отказ.
- `_build/test.static-secure-php-bridge.php`: настоящий вызов
  PHP→Python, чтение, создание, обновление, эксклюзивное создание,
  симлинки и hard links.
- `_build/test.static-secure-failclosed.php`: принудительно недоступный
  `proc_open`, отсутствие изменения файла и fallback.
- `_build/test.ci-static-toctou-installed.php`: настоящий одноразовый
  MODX 2/3, загруженный компонент, ограниченные временные файлы,
  подтверждение неизменности внешнего файла.
- Старые unit/аварийные тесты `make_static` и статического содержимого
  адаптированы к интерфейсу дескрипторного I/O.

## Ограничения

- Конкурентная запись *в тот же inode* сторонним кодом, имеющим доступ
  на запись, и DB-эффекты до/после записи требуют отдельного управления.
- Произвольные драйверы media source, внешние транспортные пакеты и
  другие прямые файловые операции вне указанных методов **не защищаются**
  этим помощником.
- Код или каталог `core_path`, которые злоумышленник может изменять
  с теми же системными правами, нельзя считать доверенной границей.
- Ограничение размера содержимого — 32 MiB на вызов.
- Отсутствие внешнего эффекта до отказа не гарантирует очистку
  частичных записей; `MUTATION_OUTCOME_UNCERTAIN` требует readback.

**Релизное решение:** подтвердить работу Python, `proc_open` и прав
доступа на типовых хостингах; для Windows либо создать эквивалентный
дескрипторный backend, либо оставить отказ. Не заменять защиту прежним
`file_put_contents()`.
