# Единый файловый backend статических элементов — тестовая MODX MCP 1.2.8

**Статус:** интегрировано PR #175 только в тестовую ветку 1.2.8; release-gates остаются открытыми. Не обновлять production, не выпускать транспорт и не сливать в `main`.

## Почему использован существующий механизм

До этой работы `StaticFileWriteSupport::replace()` выполнял portable-записи через временный файл, а `ElementMutationSupport::makeStatic()` создавал TV напрямую через `fopen('xb')/fwrite()`. Чтение `ElementContentSupport::read()` отдельно применяло `file_get_contents()`. В `StaticFileWriteSupport` также существовала небезопасная прямая запись `legacyCompatibleWrite()` при ограниченных правах/Windows/симлинках.

**Единая точка:** `StaticFileWriteSupport::read()/replace()`. Все статические элементы (chunk, snippet, template, plugin, TV) используют один контракт. Запись TV создаёт целевой файл исключительно после полного сохранения временного файла — на PHP через `link()`, в strict через дескрипторный `os.link()`. Нет параллельного `StaticFileIoSupport` или двух реализаций диспетчера.

`FilesystemSupport` оставлен для нормализации/разрешения путей. Media Source остаётся отдельной **драйверной** подсистемой MODX: `modMediaSource::createObject/updateObject/removeObject` и т. п. Напрямую переносить туда файловый backend статических элементов нельзя — S3, SFTP и другие драйверы не являются локальным каталогом.

## Настройка

`modxmcp.static_io_mode` (область security; значение по умолчанию `portable`; значения строго `portable` или `strict`). Настройка включена в transport и headless для MODX 2 и 3; при обновлении существующее администраторское значение не перезаписывается. На старых сайтах, где ключ отсутствует, предполагается `portable`.

- **portable (по умолчанию):** только штатный PHP. Существующий статический файл обновляется **без замены inode** через `fopen('cb')`, `flock`, проверку `fstat/lstat`, полную запись, `ftruncate` и `fflush`: сохраняются владелец, POSIX ACL, xattrs и обычные права доступа. Это позволяет обновлять файл даже без права создавать соседние файлы в каталоге. Для нового файла используется предварительная запись во временный файл и публикация через `rename` или эксклюзивную `link` для TV. **Обновление существующего файла не атомарно:** авария посередине записи может повредить содержимое, а посторонний редактор может проигнорировать `flock`. В таком случае возвращается `MUTATION_OUTCOME_UNCERTAIN`, без автоматического повтора. Не гарантируется устранение гонки parent-directory между проверкой и системным вызовом. Конечные симлинки и hard links отклоняются.
- **strict:** корень `core/elements` должен быть создан и защищён администратором заранее; вложенные каталоги создаёт только dirfd backend. Тот же публичный интерфейс направляет чтение, замену и exclusive create в `Security/static_io_guard.py`, адаптированный из PR #174. Каталог открывается через `dir_fd` и `O_NOFOLLOW`, запись — в приватный временный файл, публикация — через `os.replace`/`os.link` и `fsync`. Требуются `/usr/bin/python3`, разрешённый `proc_open` и Unix/Linux dir-fd API. При их отсутствии операция **останавливается**, без перехода в portable.

Оба режима проверяют, что путь относится к `core/elements` и запрещают внешние hard links; `strict` привязывает фактический I/O к открытым каталогам с O_NOFOLLOW. PHP-предобработка может канонизировать допустимый внутренний алиас, поэтому нельзя трактовать это как безусловный запрет любого исходного внутреннего симлинка. Неподдерживаемый текст настройки **не** означает portable — это явный отказ.

## Доказательства и существенные ограничения

- Статические тесты portable: создание, замена, байты, права, симлинки, hard links, запрет legacy fallback, аварийная неполная запись.
- Статические тесты strict: реальный PHP→Python, недоступный helper без fallback, инъекция короткой записи, 500 конкурентных symlink read/write. Реальные disposable MODX2/3 запускают portable **и** strict на установленном компоненте.
- **Проверено (финальный этап 1):** strict отказывает в обновлении файлов с POSIX ACL или xattrs **до изменения исходного файла**, сохраняет исходные байты и metadata; обычные mode/UID/GID сохраняются при штатной замене, чужой владелец отклоняется. CI проверяет реальный ACL, xattr, mode, owner и содержимое на одноразовой файловой системе. Это защита от потери атрибутов, а не их перенос на новый inode.
- **Ограничение portable:** обновление того же inode сохраняет ACL/xattrs/owner, но не даёт атомарного переключения всей версии файла. Читатель, который не соблюдает `flock`, может увидеть промежуточное содержимое; при частичной записи, сбое или конкурирующей модификации требуется ручная проверка. Гарантия относится к неизменности inode при штатном успешном обновлении, а не к неприкосновенности всех метаданных при участии внешнего процесса.
- Ни portable, ни strict не делают атомарными DB-процессор и файловый эффект; после записи файла и ошибки MODX сохраняется `MUTATION_OUTCOME_UNCERTAIN`, слепой повтор запрещён.
- Для portable не устранена физическая parent-dir TOCTOU гонка; при наличии враждебного процесса, способного подменять каталоги, нужен strict или отказ от записи до иной безопасной реализации.
- Для strict неизвестна совместимость всех реальных PHP-FPM хостингов и сетевых ФС; не включать в production до тестов прав, owner/ACL, Linux/Windows и реального PHP-FPM.
- Для внешних media driver и PackageSupport безопасность должна проверяться отдельно. Единый static backend не является универсальным rollback файлового API.

## Правило релиза

PR #175 интегрирован **только** в `feature/1.2.8-cas-pr46-20261121` после зелёных CI 4/4, disposable 12/12 и upgrade 2/2. `main` не трогать. Любой переход `portable`→`strict` — явное действие администратора; silent fallback запрещён.

## Совместимость обновления 1.2.7 → 1.2.8

Обычный владелец MODX не устанавливает Python, Node, FFI, не включает `proc_open` и не перенастраивает сервер ради записи static-элементов: настройка `portable` используется по умолчанию. Не включать `strict` автоматически ни при установке, ни при обновлении. Ветку `strict` считать специализированной явной настройкой предыдущих тестовых сборок, не нормой для массового релиза. Никаких скрытых попыток переключать режимы.

**Критерий:** «необходимое и достаточное» усиление на штатном PHP, честные коды отказа и документированные остаточные риски. Математической гарантии при конкурентных враждебных процессах нет.
