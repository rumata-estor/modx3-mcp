# MODX MCP — программа усиления безопасности

**Статус:** перечень проверок и предложений; НЕ подтверждение, что проблемы исправлены.  
**Ветка:** `feature/mcp-security-hardening`.  
**Охват:** MODX Revolution 2.8.x и 3.x, единый репозиторий `rumata-estor/modx3-mcp`, платформенные различия тестируются отдельно.  
**Согласованная общая архитектура:** [SITE-AGENT-INTEGRATION-REQUIREMENTS.md](SITE-AGENT-INTEGRATION-REQUIREMENTS.md).  
**Связанная разработка:** [Site Agent](https://github.com/rumata-estor/site-agent-runtime/tree/feature/agent-permission-control/docs/security).

Слияний, развёртывания на рабочих сайтах и изменений версий в рамках создания ветки нет. Документ служит исходным backlog для последующей реализации и отдельного согласования технических решений.

## Граница ответственности

**Site Agent** — поручения, план, подтверждение человека, одноразовые разрешения, пауза/отмена, аудит исполнения.

**MODX MCP** — реальные серверные ограничения операций, аутентификация API, минимальные разрешения, права MODX, защита файлов/сниппетов/процессоров и проверка фактического эффекта. Выданный агенту токен не должен автоматически означать разрешение на любую запись.

## P0 — проверить и закрыть до эксплуатационных испытаний

1. **Служебный пользователь и права MODX.** В текущем коде при `modxmcp.service_user_id=0` подбирается активный sudo-пользователь. Проверить переход на минимальные сервисные права и отказ вместо повышения привилегий; MODX ACL должны применяться в точке выполнения каждого действия.
2. **Идентификация и область действия токена.** Сейчас REST API использует общий `modxmcp.api_token`. Проработать разграничение токенов по пользователю/сайту/действию, срок действия, отзыв, хранение только защищённых представлений и журнал авторизованных запросов. Не полагаться только на общий bearer token.
3. **Исполняемый код.** Различать сохранение PHP, активацию сниппета/плагина, привязку к событиям и запуск кода. Отдельно проверять косвенные эффекты, права процесса, доступ к ядру и возможность обхода ограничений изнутри PHP. Простая проверка расширения или PHP lint не защищает от побочных эффектов.
4. **Универсальные процессоры.** `run_processor` по умолчанию выключен настройкой `modxmcp.allow_run_processor`. Проверить, что никакой разрешённый инструмент не открывает аналогичный путь к произвольным системным/компонентным процессорам; отдельно проверить `processors_path`, вызовы custom processors и цепочки через сторонние дополнения.
5. **Все ветви обработчика.** В `modxmcp.class.php` есть модульное ядро и старый обработчик/fallback. Защита должна быть эквивалентна в обеих ветвях; при отказе нового контрольного слоя не должен автоматически включаться менее защищённый путь.
6. **Прямое обращение к API.** Проверить, может ли клиент с действующим токеном выполнять запись в обход нового механизма согласования Site Agent. Нужна ясно определённая граница: ограниченный токен исполнителя, серверный policy gate или иной независимый проверяемый механизм. Одних запретов в промпте Site Agent недостаточно.
7. **Запись файлов и медиа.** Проверить allowlist каталогов и media sources, realpath/symlink, двойные расширения, `.user.ini`, `.htaccess`, PHP-файлы, MIME/содержимое, ограничения размера и права файловой системы. Запрет на запись в ядро должен быть реальным, а не только по имени пути.
8. **Изменение прав и защитных настроек.** Защитить токены, ACL, собственные настройки безопасности и системные настройки MODX от опосредованного повышения полномочий через обычные операции с объектами/процессорами/пакетами.
9. **Повторы, пакеты и частичные ошибки.** Атомарные предусловия, CAS, уникальный idempotency key, состояние каждой операции и запрет слепого повтора после неизвестного результата — на уровне реального исполнителя.

## P1 — после устранения блокеров

- Ограничение запросов и защита от перебора токенов; корректный HTTPS, доверенные proxy и IP allowlist.
- Маскировка секретов в ответах, сообщениях об ошибках, журналах и резервных копиях.
- Сетевые запросы, SSRF, обращение к локальным адресам и утечка данных наружу.
- Prompt injection через имена ресурсов, контент, описания и tool responses: никогда не повышает привилегии.
- Тесты с различными политиками пользователей MODX, версиями CMS, установленными дополнениями.
- Аудит фактически выполненных изменений, проверка исхода и удобные сообщения об отказе человеку.

## Наблюдения, не перепутать с доказанными уязвимостями

- В исходниках обнаружены общий API-токен и подбор sudo-сервисного пользователя по умолчанию. Это реальные характеристики кода; возможность конкретного обхода ещё требуется испытать.
- `run_processor` присутствует, но по умолчанию выключен. Это потенциально опасный механизм, а не доказательство, что он сейчас доступен.
- Модульный runtime и fallback требуют сопоставления разрешений. Само существование fallback не доказывает его эксплуатацию.
- В нашем репозитории **одна общая кодовая база для MODX 2 и MODX 3**, поэтому новый механизм безопасности необходимо тестировать в обеих версиях отдельно.

## Что полезного подсмотрено у других

- `karamble/modxmcp`: token scopes, проверка MODX ACL, default-deny для загрузки файлов, запрет серверно-исполняемых расширений; PHP в сниппетах/плагинах всё же сохраняется через processors.
- `ShevArtV/mxboard`: привязка токена к пользователю, общий сервисный слой MCP/REST.
- `dampilov94/mcp-component`: защита повторных запросов и idempotency.
- `ldrshv/ai-editor`: схема preview → apply.

**Источники:** https://github.com/karamble/modxmcp · https://github.com/ShevArtV/mxboard · https://github.com/dampilov94/mcp-component · https://github.com/ldrshv/ai-editor

## Первый шаг по этому репозиторию

Только read-only инвентаризация точек входа, механизмов прав и PHP/processor/file capabilities; составить таблицу `действие → право → проверка → обход → тест`. Реализацию начинать после согласования интерфейса с Site Agent и политики fallback. Отдельные ветки остаются открытыми до полноценного тестирования; номер следующей версии пока не определяется.
