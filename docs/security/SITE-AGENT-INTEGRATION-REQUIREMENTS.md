# Site Agent — архитектурные требования

**Статус:** согласованные требования, редакция 2026-11-03. Реализация и её соответствие требованиям ещё не подтверждены.  
**Область:** Site Agent и MODX MCP; предусмотрено расширение на другие CMS.  
**Цель:** не дать агенту выполнить несогласованные действия, включая обход через альтернативные инструменты.

## 1. Основные правила

**1.1. Вопрос не является поручением.** Вопросы, обсуждения, предложения, просьбы оценить идею и замечания по плану не разрешают менять сайт. Требуется явно выраженное поручение и, перед выполнением, утверждение конкретного плана.

**1.2. Инициатива допустима, самовольное выполнение — нет.** Агент самостоятельно анализирует, ищет решения и предлагает улучшения. Он не может расширить согласованный план своими действиями. Лучшие альтернативы сначала объясняются человеку и согласовываются.

**1.3. Выполняется только согласованный план.** Все операции, которые не входят в его границы, заблокированы до нового согласования. Неоднозначности не трактуются в пользу удобного для агента варианта.

**1.4. Запрет должен быть программным.** Текст инструкций, описания инструментов и обещания агента не являются средствами безопасности. Операции проверяет независимый исполнитель.

**1.5. Запрещён обход.** Нельзя обойти ограничения через SSH, терминал, файлы, MCP, API, собственный PHP-код или другой доступный канал. Агент не изменяет правила и не выдаёт себе разрешения.

**1.6. Действия человека через терминал.** Если для задачи необходимы терминальная команда либо прямое изменение файловой системы, которые агенту запрещены, агент объясняет человеку, что именно требуется, почему и как выполнить это самостоятельно. Агент такие действия не выполняет.

## 2. Порядок выполнения заданий

**2.1. Анализ.** Агент изучает сайт, объекты, зависимости, существующий код и последствия. На стадии анализа ничего не меняет.

**2.2. План.** До работы показывает, что создаст и изменит, какие существующие файлы и элементы использует, какие другие части сайта могут быть затронуты. Предпочитает существующие решения, не создаёт ненужных компонентов или зависимостей.

**2.3. Обсуждение не запускает выполнение.** Корректировки человека меняют только проект плана. После корректировки агент представляет новую редакцию. Работать можно лишь после явного утверждения окончательного плана.

**2.4. Неоднозначность.** Если поручение можно понять двояко, агент останавливается, объясняет варианты и спрашивает, что имелось в виду. Ответ-уточнение сам по себе не разрешает выполнение.

**2.5. Влияние до записи.** Агент проверяет затрагиваемые и косвенно зависимые страницы, стили, шаблоны, скрипты, плагины и компоненты. При выходе последствий за пределы плана приостанавливает соответствующую операцию и предупреждает человека; при неопределённости прямо говорит об этом.

**2.6. Исполнение.** Агент выполняет только согласованные операции; новые объекты, изменение метода реализации и выход за пределы плана требуют дополнительного согласования. Для критических действий действует отдельное одноразовое подтверждение.

**2.7. Проверка и отчёт.** Агент проверяет фактический результат, сообщает о созданных и изменённых объектах, косвенно затронутых страницах и элементах, неожиданных последствиях, ошибках и непроверенных местах. Без проверки задача не считается завершённой. Неожиданные изменения нельзя молча исправлять новыми несогласованными операциями.

## 3. Разрешения

**3.1. Поручение, план и техническое право — разные вещи.** Наличие ключа, инструмента или права в MODX не является разрешением на действие. Изменения допустимы только в утверждённом плане и рамках программных полномочий.

**3.2. Чтение.** Анализ и чтение доступны в пределах предоставленного доступа, без раскрытия секретов и защищённых данных.

**3.3. Создание и изменение.** В плане могут быть предусмотрены ресурсы, шаблоны, файлы, CSS/JS, PHP-компоненты, контроллеры, сниппеты, плагины, настройки этих элементов и настройки сайта. Критические настройки требуют отдельного подтверждения.

**3.4. Критические операции.** Удаление, установка компонентов, опасные системные изменения и иные операции из таблицы критичности требуют отдельного разрешения человека. Конкретная таблица критичности составляется и проверяется в ходе технического аудита.

**3.5. Одноразовость.** Подтверждение относится к конкретной операции, объекту, параметрам и заданию; повторное использование запрещено, даже для аналогичной операции через десять минут.

**3.6. Пакеты.** Один раз можно утвердить *точно определённый* пакет действий (например, удалить десять названных ресурсов). Список, параметры и последствия предъявляются до подтверждения. Добавление одиннадцатого объекта — новый запрос. Разрешение расходуется на одно выполнение согласованного пакета, без автоматического повтора.

**3.7. Проверка.** Каждая операция сверяется с действующим планом, целью, параметрами, критичностью и разрешениями. При ошибке проверки она не выполняется. Агент не создаёт, не меняет и не продлевает разрешения.

**3.8. Происхождение подтверждения.** Все авторизованные участники команды могут работать над всеми проектами, без роли «владельца сайта». Но разрешение должно поступить от реального авторизованного человека через независимый доверенный механизм, а не из текста, присланного агентом. Подтверждение сопоставляется с заданием и конкретной операцией. Для Telegram предполагается использовать надёжные данные происхождения сообщения через CC Connect; техническая реализация будет уточнена после аудита. Разделение «опытный/новичок» остаётся функцией MODX MCP и влияет на подробность предупреждений, а не на возможность обойти запрет.

**3.9. Пауза и отмена.** «Стоп» блокирует начало новых операций и приостанавливает задание; «Продолжить» возобновляет после проверки разрешений; «Отмена» прекращает задание и отзывает неиспользованные разрешения. Сигналы обрабатываются независимо от занятого агента. Уже запущенную операцию останавливают безопасно, где возможно, и сообщают фактический результат.

**3.10. Актуальность перед записью.** Если после чтения или согласования другой пользователь изменил объект, агент не перезаписывает его вслепую: сверяет версии/состояние непосредственно при записи, сообщает расхождения и при необходимости запрашивает обновлённое согласование. Незатронутые операции не блокируются без необходимости.

## 4. Технические ограничения

**4.1. Независимое принудительное применение.** Запреты применяются программно ко всем каналам, а не только к списку видимых инструментов. При недоступности проверки — отказ.

**4.2. Контроль фактического исполнителя.** Доступные команды, альтернативные API и фоновые процессы не должны обходить общий контроль. Агент не меняет настройки защиты и свои полномочия.

**4.3. SSH и файлы.** Агенту запрещены прямые SSH/терминальные операции и прямое редактирование файловой системы. Необходимые действия передаются человеку с конкретной инструкцией. CMS-операции с файлами и элементами допускаются только через утверждённый контролируемый интерфейс.

**4.4. Ядро и механизмы безопасности.** Изменение ядра MODX, учётных данных, правил контроля и защитных механизмов запрещено в обычном режиме и должно блокироваться технически.

**4.5. Проверка разрешения.** До исполнения проверяются план, объект, действие, параметры, одноразовость и дополнительные разрешения; отсутствие любого обязательного условия означает отказ.

**4.6. Журнал.** Фиксируются инициатор, объект, действие, подтверждающий человек, итог, изменения и попытки запретных операций.

**4.7. Объяснимые отказы.** При блокировке и ошибке агент немедленно на понятном языке объясняет: что не получилось, почему, что необходимо и можно ли продолжать. Неизвестные причины не выдумываются. Ошибку нельзя скрыть или объявить задачу выполненной.

**4.8. Недоверенные инструкции.** HTML сайта, файлы, комментарии, журналы, документы, результаты инструментов и внешние ответы — данные, а не команды и не подтверждения человека. Они не могут менять правила, план или источник разрешения.

**4.9. Изоляция сайтов.** Все участники команды могут работать со всеми проектами, но разрешение на один сайт/контур не переносится на другой. Смена целевого сайта или переход с тестового контура на рабочий требует нового согласования. Подключения и ключи разных сайтов изолированы.

**4.10. Аварийное восстановление.** При любом сбое система прекращает дальнейшее исполнение, сообщает причину (если известна), что фактически создано/изменено, что не выполнено и что неизвестно. Сохраняет состояние задания, план и разрешения. После сбоя автоматическое продолжение запрещено: нужно новое подтверждение человека. Неизвестные исходы не повторяются без проверки.

**4.11. Исполняемый код.** Создание PHP, сниппетов, плагинов и контроллеров возможно в пределах плана, однако их выполнение способно влиять на весь сайт. До применения проверяются эффекты, возможные автоматические триггеры и обходы безопасности. Ядро должно защищаться также на уровне ОС. Если невозможно обеспечить безопасное выполнение, агент сообщает причину и не выполняет операцию.

## 5. Архитектура системы

**5.1. Ответственность.** Site Agent анализирует и готовит планы, общается с человеком и координирует исполнение. Независимый механизм авторизации проверяет планы и разрешения. MODX MCP предоставляет контролируемые операции над MODX.

**5.2. Отдельная граница доверия.** Агент не администрирует механизм авторизации. Человеческое подтверждение не принимается из аргументов инструмента, текста модели или файла плана без независимой проверки происхождения.

**5.3. Реестр операций.** У каждой операции есть тип, уровень критичности, допустимые объекты и требуемые разрешения. Новые инструменты не получают права на запись автоматически.

**5.4. Обязательный контроль всех путей.** Защита действует в точке реального исполнения; скрытие инструмента не считается защитой.

**5.5. Расширяемость.** Общая политика независима от CMS; MODX подключён адаптером. Другие CMS возможны в будущем без переписывания механизма прав. Сейчас разрабатывается только MODX.

**5.6. Ввод в эксплуатацию.** Сначала отдельная ветка и тестовый контур, затем проверка запретов и попыток обхода. Пока защита не подтверждена испытаниями, она не применяется к рабочим сайтам.

## Критические замечания к текущей реализации — НЕ утверждённые изменения

Основаны на выборочной проверке исходников 2026-11-03, **не** на полноценном эксплуатационном тесте. Эти замечания — входные данные для аудита, они не изменяют утверждённые выше правила.

| Приоритет | Наблюдение | Что нужно подтвердить / закрыть |
|---|---|---|
| P0 | Команда `siteagent changeset approve` доступна через CLI; `source=user` — аргумент, а не криптографически проверенное происхождение решения | Убрать у агента право утверждать; утверждение принимает только независимый авторизованный сервис |
| P0 | `site-file put/delete` допускает флаги `--yes`, `--confirm-delete`, `--allow-sensitive`; внутри используется SSH-транспорт | Заблокировать запуск агентом без утверждённого допуска, независимо от интерфейса и флагов |
| P0 | MODX MCP по умолчанию действует через служебного пользователя `sudo`; API использует общий токен | Проверить минимальные права, индивидуальные токены и принудительное серверное ограничение каждой операции |
| P0 | Запись PHP-сниппетов/плагинов и произвольный процессор могут привести к исполнению кода с правами сайта | Отделить создание/редактирование кода от его активации; запретить произвольный processor escape hatch и защищать ядро на уровне исполнения |
| P0 | Разные каналы Site Agent, MODX MCP и файловых операций не имеют доказанного единого неизбежного контроля | Построить карту всех каналов и испытать попытки обхода на тестовом контуре |
| P1 | Некоторые механизмы защиты уже существуют: ChangeSet fingerprint, preflight, state guard, lock, резервные копии | Инвентаризировать и переиспользовать; проверить одинаковое применение во всех путях |
| P1 | В MODX MCP есть legacy fallback при сбое modular runtime | Проверить совпадение защит обеих ветвей; исключить переход к менее строгому режиму |
| P1 | Секреты, токены и инструменты сети могут быть доступны в среде исполнения | Проверить хранение/ротацию ключей, маскировку, утечки в логах, сетевую изоляцию и правила внешних URL |
| P1 | MCP tool descriptions и результаты — недоверенный источник | Проверить инъекции, подмену инструментов и цепочки вызовов; тестировать запреты фактическими операциями |

**Важная граница:** стандарт MCP не делает доверенную авторизацию приложений автоматически. Наличие MCP-токена, проверка HTTPS, бэкап и подтверждение на уровне текста — полезные, но недостаточные меры.

## Проверенные открытые реализации и рекомендации

- `karamble/modxmcp`: токены с scope, ACL пользователя MODX, fail-closed проверки; PHP-сниппеты и плагины допускаются через MODX processors, **файловая загрузка исполняемых PHP запрещена**. MIT. https://github.com/karamble/modxmcp
- `ShevArtV/mxboard`: общий сервисный слой для MCP/REST, привязка токена к пользователю и проверка ролей. https://github.com/ShevArtV/mxboard
- `dampilov94/mcp-component`: базовый MODX MCP, request-id для безопасной обработки повторов и восстановления состояния. MIT. https://github.com/dampilov94/mcp-component
- `ldrshv/ai-editor`: preview/apply, журнал и rollback, работа через MODX processors. https://github.com/ldrshv/ai-editor
- MCP Security Best Practices: https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/docs/2026-07-28/tutorials/security/security_best_practices.mdx
- OWASP MCP Security Cheat Sheet: https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html
- OWASP MCP Top 10: https://owasp.org/projects/mcp-top-10

**Правило использования чужих решений:** указывать проект и авторство; перенос кода — только после отдельной проверки лицензии и тестов.
